# N17 时间机制离线归因

问题：N16 TimePlan 成功率和成本均未过门槛，需要判断拦截是否针对真实时间错误。

方案：仅审计 N16 v5 dev 的360条增强轨迹，按公开时间表重放注册提案，分别记录时间检查T、结束回执R与元数据拒绝；不查看新留出任务。

结果：60次运行覆盖20个独立任务，共123行时间表；412次提案重放与在线检查一致。T触发300次、涉及19个任务，其中291次（97%）因缺step映射，只有9次是注册时间与表冲突，涉及2个任务。R触发33次、涉及9个任务；元数据拒绝31次。未完成20次，查询预算耗尽0次。

案例：case48 seed42的公开表正确分开+22/+30/+51分钟，但4次注册缺refs被拒，随后3次finish无注册回执；G/TimePlan均失败，模型调用9→12，tokens57,003→96,711。case34 seed43将+5/+17合并，8次冲突后仍重复提案。前者还有设备映射问题，不能直接判为语义误拒。

决策：拦截主要体现元数据负担；重放一致不证明语义误拒/漏检为零，捆绑实验也不能分离prompt、T、R的因果贡献。依据计划的成本增加及留出不足停止条件，结束离线诊断，不跑四臂在线消融，不进入N18。

证据：`runs/time-plan/n17-v1/audit.json`、`runs/time-plan/n16-v5/case-review.json`；脚本`scripts/audit_time_plan_mechanisms.py`（`7085250`、`27baf1e`）。节点提交见`git log -- docs/nodes/N17.md`。
