## 当前结果对下一步的约束

- B0/H1 三轮均为 12/16，没有逐任务成功翻转。四项调光任务持续失败。
- H1 每轮非法动作 24 次，B0 为 20 次；生成 tokens 高 5.20%，模型调用高 1.72%。
- H1 的外层参数错误证据减少，但设备命令语义错误增加。仅加外层 schema 未解决主要失败。
- 成功任务子集中 H1 的生成 tokens 略低（每轮 399322 vs 399517）；总体额外成本主要来自失败任务，不能笼统解释为 schema 总是更贵。
- 这些是 16 项已用于工程开发的任务重复三次，不能当成 48 项独立样本或泛化成绩。

## 建议的后续顺序（全部待 review，当前不执行）

### 1. 先建立可维护的工程入口

建议明确一个可编辑的项目工作树及版本基点，保留 P1 包为不可变证据；把历史 1.5B/32B/custom agent 入口与当前 9B 入口明确标注。项目根目前没有 Git 元数据，本机 source-p1 是快照而非完整可安装 checkout，直接继续堆改动会使差异和回滚难以追踪。

随后处理只读核验与输出目录分离、过期文档、固定日期/运行目录、embedding 依赖声明。每项单独验收，保持实验协议和已有结果不变。这些是建议的后续维护工作，本轮没有初始化 Git、移动文件或修复脚本。

### 2. 优先设计设备能力反馈的最小对照

优先理由：持续失败集中在调光；错误证据直接指向命令内部参数与只读属性，外层 JSON schema 不表达这些能力。候选是在原工具返回的设备结构中补充可核实的命令参数名、类型及只读信息，固定其来源，比较成功率和新增 token 成本。

必须先确定：以修复后 B0 还是 H1 为比较基点、是否所有变体共享同一能力数据、任务仍用哪份冻结 dev、预算是否不变。不要同时开启 finish guard、恢复提示与能力反馈后把收益归因于单一机制。错误反馈对照应作为另一个预先规划的比较，不在结果不佳后临时追加。

验收至少包括：源信息正确、无静默动作修复、无目标泄漏、完整失败保留、真实状态成功检查、全部/成功子集成本与独立核验。

### 3. 再规划数据与训练

先冻结训练和评估任务的独立划分、轨迹契约及筛选规则，再做小规模 SFT；只有数据、训练过程与评测可核验后才计划 RL。P1 轨迹可以作为研究材料，不能未经审查直接作为正式训练集。
